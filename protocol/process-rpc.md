# Process RPC 方案

状态：远端 Process 首版已实现，采用共享 WS 请求、输出事件和 terminal 响应。字段以 [process.proto](remote/v1/process.proto) 为准；实现见 [Client](../go/remote/process_client.go) 与 [Server](../go/remote/process_server.go)。使用与验证见 [执行指南](../docs/development/execution.md)。

读取触发：实现命令 RPC、输出事件、执行登记、取消竞态、断线确认或 stdio 事件桥接。两端组件、目标绑定与关闭所有权见 [远端执行器架构](../docs/architecture/remote-executor.md)。本机 Runner 内的 Remote Process 是 RPC 调用方，独立远端 Go 执行器是 RPC 服务端；Bash 只在目标侧启动。

## 传输选择

Exec 是同一 WS 上的一个请求、连续输出事件及一次终态响应，按 request_id 分发成逻辑输出流，不为每次执行创建物理连接。一次性、无交互 Bash 不需要 stdin 或 PTY；WS 支持双向消息不扩展公共 Process 能力。

请求信封、心跳、队列与控制范围以远端通道方案为准。控制操作是同一 WS 上拥有独立 request_id 的调用，不另设 HTTP 或第二条控制连接；旧连接断开后 SDK 立即报错，不为原调用建立替代连接或查询。

TS 到本机 Runner 保留 stdio，与这里的 Go 到远端服务分开处理。输出事件由 Runner 转换为 stdio 消息，不把 protobuf 或远端错误直接交给 Pi。

## RPC 操作

| 操作 | 形式与职责 |
| --- | --- |
| process.exec | 请求 + started / output 事件 + terminal 响应，共用 WS 上的逻辑流 |
| process.cancel | 普通请求响应；请求停止指定执行，确认已收到取消请求 |
| process.getState | 普通请求响应；在原 WS 仍连通且逻辑输出取消后查询受管理执行是否已结束 |

Cancel 的确认不是进程终态。独立控制请求可以在逻辑输出等待取消后继续使用共享 WS；它不代表独立物理通道。若 WS 已失效，原调用立即失败，不重连查询或取消。关闭 WS 本身不证明目标已停止，执行器必须落实清理。

## 执行身份与输入

| 字段 | 语义 |
| --- | --- |
| 业务版本 | 在 WS 子协议与应用握手中协商为 v1，业务消息不再重复携带 apiVersion |
| executionId | 客户端在发送前生成的执行 ID；用于 exec、cancel、getState 及输出事件关联，不向 Agent 暴露 |
| targetId | Remote Environment 绑定的远端目标，不能由 Agent 文件或命令参数随意改变 |
| serviceInstance | 已协商的远端服务实例引用；执行器每次启动使用新实例身份，防止旧请求在重启后的服务启动 |
| admissionExpiry | 本次启动接纳的有限有效期；由执行器签发的接纳租约表达，随通道请求内部元信息发送，服务端按自己的时钟校验 |
| command | Bash 脚本文本 |
| cwd / env | 本次执行的工作目录与环境变量覆盖项 |
| timeoutMs | 目标运行预算；服务端执行截止时间，不等同于客户端停止等待 |
| maxOutputBytes | SDK 最终保留的双流合计上限 |

传输 requestId 与 executionId 分别关联 RPC 调用及目标执行。实际 Session、serviceInstance、targetId 和 executionId 共同关联执行与控制，不引入用户身份或权限；本机环境保留自己发起的 executionId，环境关闭只控制这些执行。

serviceInstance 与 admissionExpiry 属于远端适配器内部控制元信息，不增加公开 ExecRequest 字段。实例绑定及接纳租约通过连接准备和能力查询取得，接纳期限不因排队、重连或清理确认而延长；服务端在进入启动阶段前再次校验期限及上下文。取消先到时携带同一次执行原有租约，取消标记保留期必须覆盖该 ID 的最晚接纳期限；标记过期后到达的旧 Exec 也必须因接纳期限失效而被拒绝。RPC 的 timeoutMs 不能单独表达最晚启动时刻，不依赖两端时钟同步或本机停止等待来拒绝迟到请求。

已接纳 executionId 的去重信息同样至少保留到该 ID 的接纳期限失效，与完整终态查询缓存分别管理。例如快速命令的 2 分钟终态缓存已经过期、但启动接纳期尚未结束时，仍保留拒绝重复启动的简要标记；GetState 可以报告记录过期，迟到的同 ID Exec 仍拒绝启动。不能因为查询缓存被清理而让旧执行再次产生副作用；两类状态都必须计入有界容量。

服务端校验实际 Session、目标、参数、限制、实例与接纳期限后，原子登记执行再进入启动阶段。记录保留期间拒绝重复 exec ID，不重放命令；该检查不声称提供跨重启的持久幂等性。Exec 不做自动重试、并行重发或断线补发，WS 断线立即失败，不自动重连或重放原 Exec；不能把同一 executionId 的第二次到达解释成新的执行。

取消先到达时，服务端在同一执行注册边界记录有界的取消标记；随后相同 ID 的 Exec 在启动前失败。标记和登记必须协调，不能使用“查询不存在后再写标记”的两个无锁步骤。已登记执行收到取消时，登记表触发该执行的取消器；已终止的执行收到取消保留原终态。

Cancel 返回“停止请求已登记或提交”的确认，不能以找不到活动执行推断其从未运行。标记容量不足时明确拒绝控制请求，客户端报告确认失败；不能在未保存标记时谎报取消成功。控制请求不占普通执行的并发额度，但拥有独立且有界的容量与截止时间。

启动与取消的协调不靠持有登记表锁执行整个 OS 调用。登记先持有可取消的执行上下文与内部执行范围；若取消与 OS 启动并发且进程已经创建，执行侧必须把它纳入清理，再确认终态。

## 输出事件

| 类型 | 内容 |
| --- | --- |
| started | Envelope.event，name=process.started；executionId，信封序号；说明目标已启动，不暴露 OS PID 作为控制句柄 |
| output | Envelope.event，name=process.output；executionId、stdout/stderr 标识与字节片段，信封序号 |
| terminal | Envelope.response.body；完成确认、可选退出码/信号、耗时、输出标记与可选执行错误，信封序号 |

每次执行的事件及终态使用信封 sequence 从 1 连续递增，output 在 terminal 前发送；启动前失败可以直接发送 terminal。started / output 不结束请求等待，terminal 已经是唯一 response，不另发送第二条完成消息。只有 WS 关闭或逻辑流 EOF 而没有 terminal 时，不能默认命令成功；能够明确确认启动前拒绝的 RPC error 按权威 not_started 处理。

started 在目标进程确实启动并进入管理范围后产生。公开 Process.Exec 只有输出回调与返回值，因此 Local Process 和远端执行器需共享内部执行内核，由它向执行登记表提供启动与清理状态通知；不能以登记成功、调用 Exec 或第一条输出替代启动确认。公共 Process 不增加启动回调或执行句柄。空输出命令仍能收到 started；内部缓冲保证 started 在 output 前发送。

输出以 WS Binary Message 中的 Protobuf bytes 传输，JSON 边界才需要 base64。各流内保持顺序，跨 stdout / stderr 顺序只是执行服务的观察顺序。客户端将输出送入捕获缓冲与可选回调，按流增量解码文本。

terminal 不重复携带整个 stdout / stderr，Remote Process 用已收到的事件构造 Go ExecResult。getState 只恢复终态元数据，不重放丢失的输出；发生丢失时设置 OutputIncomplete。

执行侧先保存可确认的结果，再尝试发送 terminal。网络发送失败不抹去已经确认的退出或清理信息。客户端校验事件关联与递增序号，无法确认完整性时标记 OutputIncomplete；不能把重连流拼成一次完整输出或自动重发 Exec。

非零退出码是正常 terminal 中的执行结果，不转换成 RPC 服务失败。启动、取消、超时等执行错误在 terminal 中表达；无法收到 terminal 的网络错误在客户端转换为连接或结果不确定错误。

## 取消、断线与状态记录

- 单次 Exec 取消时，执行服务尝试停止该执行；共享 WS 断线时，清理该连接会话拥有的未结束执行，不按 targetId 取消其他会话的命令，不能将它默认为后台任务继续运行。
- SDK 用户 ctx 取消时使用独立的清理上下文发送 cancel 并等待终态或 getState，不用已经取消的上下文执行确认请求。
- 若共享 WS 仍可读，优先等待 terminal 或在独立清理预算内 getState；一旦断线直接报错，不重连确认。未收到权威终态的已发送执行返回 unconfirmed / OUTCOME_UNKNOWN；查询失败、缺记录也不证明命令未执行。
- 服务端运行预算结束后也负责终止和清理。网络恢复不会自动重新执行命令。
- 服务端保存有界的活动状态与近期终态；确认管理范围结束或确认未启动后，初始终态保留 2 分钟，默认策略见 v1 契约。unconfirmed 后仍待回收的执行继续占活动容量，不能按近期终态过期移除；容量满时在启动前拒绝新的执行，不提前驱逐仍承诺可查询的终态。
- 记录不持久化。服务重启产生新 serviceInstance；旧实例 Exec 必须拒绝启动，旧实例查询明确无法恢复。记录缺失、过期或实例变化都不证明命令未执行，未确认的命令返回 OUTCOME_UNKNOWN。
- State 查询明确区分登记/启动中、运行中、清理中、已确认终止、启动前结束与缺记录；只有确认过管理范围结束才能映射 finished。
- Exec 清理宽限结束可以先返回 unconfirmed；执行内核和登记表继续持有存活进程句柄、取消与回收责任，不把它从活动集合中当作完成删除。后续 GetState 可以报告后来确认的状态，但不补发第二个 terminal 或重放日志。

| GetState 观察 | 客户端处理 |
| --- | --- |
| 登记/启动中、运行中、清理中 | 继续有限确认；截止时仍未确认则返回 unconfirmed |
| 启动前已结束 | 使用权威的 not_started 与错误；不是以缺记录推导 |
| 管理范围已结束 | 使用权威结果及执行错误；丢失输出保持 OutputIncomplete |
| 缺记录、已过期或服务实例不匹配 | 返回 unconfirmed / OUTCOME_UNKNOWN |

运行预算、RPC 等待、启动接纳期、WS 心跳 / I/O 预算及清理宽限分别设置。Remote Process 在发送前扣除本机已经消耗的运行预算，目标计入自己的排队时间并使用剩余预算与服务限制，不恢复完整时长；两个宿主的计时不能替代服务端租约校验。RPC 等待保留清理与终态发送机会；用户 ctx 取消触发停止请求，确认请求使用独立有界上下文，不能把该请求 ctx 直接用作共享 socket 的读取上下文。

首次查询、取消、记录保留与所有者关闭都需要验证竞态。任何生命周期状态都不代表文件副作用会回滚。

服务端在收到单次取消或知道共享连接失效后发起对应目标清理；网络故障的检测不保证立即完成，因此仍以目标运行预算限制无人接收的执行。服务端进程崩溃时旧登记不再可查；自动重启不构成原命令已停止的证据。

## 输出限制与慢消费者

默认输出片段 64 KiB，最终捕获 1 MiB、最大捕获和总转发均为 8 MiB，每执行输出队列 1 MiB / 128 条；完整数值见 v1 契约，后续联调验证编码边界。执行侧配置有界输出队列与总转发上限，SDK 的最终捕获上限独立设置。

管道读取与网络发送分开。队列或总转发上限达到时，保留已经排队的输出、停止转发此后全部输出并标记截断，继续排空目标输出；不能丢掉中间片段后又恢复转发，让结果伪装成连续前缀。不能为了保留所有日志而无限积累内存或停止管道消费。事件序号按实际发送的事件生成，terminal 保留独立发送机会。

Local Process 内部输出回调只向有界发送队列提交数据，不直接执行阻塞的网络发送。客户端网络读取与用户回调也要有界协调，保留返回后不再调用回调的契约；无限阻塞的用户函数不能通过新建 goroutine 无限堆积规避。总转发量不足或队列丢弃导致保留输出缩短时，由 terminal 的 OutputTruncated 表达；连接丢失等未知缺口另设 OutputIncomplete。

发送与控制等待都有截止时间。最终事件无法发送且共享 WS 已失效时触发会话清理，客户端立即报告结果不确定，不重连查询；原 WS 仍可用但未收到终态时，才在独立清理预算内通过状态查询确认结果。完整日志持久化和断线续传不属于第一版。

WS 写调度器为控制与终态预留额度，多个请求间公平发送；不让本次 terminal 越过已排队的本次输出。单连接的 TCP 阻塞不能由优先队列完全消除，因此输出片段、写入预算与队列都必须有界。详细调度和连接级故障范围见 [通道方案](remote-channel.md#单通道调度与背压)。

## stdio 接入

当前 [stdio 解析器](../src/protocol.ts) 接受 result / error / process.output 事件，[客户端](../src/client.ts) 捕获双流字节并在终态后删除活动请求。Runner 转换 WS 事件与终态，不直接转发远端信封。

这项变化需要同步两端类型、版本或能力协商、客户端等待预算及测试。不得将设计中的事件直接描述为当前 v1 已支持的消息。命令 stdout / stderr 编码成事件，不能直接混入 Runner 的协议 stdout。

stdout / stderr 字节在 stdio JSON 中需要明确编码。Runner 结果也必须遵守编码后的消息上限；当前 1 MiB 的捕获默认可能超过 1 MiB JSON 消息限制，不能直接整块塞入终态。应沿用分块事件，由 TS 重建受限输出，终态只传摘要。

## 验证与实现前事项

验证执行前取消、取消登记竞态、取消标记过期后迟到 Exec 被拒绝、重复 ID、实例重启后的旧请求、退出与取消竞态、慢消费者、双流输出、子进程清理、unconfirmed 后持续回收、网络中断、终态丢失、记录过期，以及多个环境共享连接时关闭其中一个。

消息字段以 [process.proto](remote/v1/process.proto) 为唯一来源，握手、租约和默认值见 v1 契约。实施时确定 WS / Protobuf 库与 Go 生成方式并扩展 stdio；Server 配置暂留，第一版不做身份权限或自动重连。生成代码、网络服务和实际两进程测试已提供；Windows / Linux 运行行为仍需验证。
